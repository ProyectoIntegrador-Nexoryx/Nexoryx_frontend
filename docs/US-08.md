# US-08 — Unirse a una sala

## Alcance y arquitectura existente

US-08 reutiliza la infraestructura que TS-02 ya tenía: `GET /api/v1/rooms/:roomId`, el handshake autenticado de Socket.IO, los eventos `room:join`/`room:leave`, acknowledgement, `participant:joined`/`participant:left`, `PresenceService` y la página de llamada. No se añadió otro gateway, socket ni modelo Firestore.

La ruta existente `/rooms/:roomId` se mantiene como URL canónica porque ya la usan creación de salas y enlaces del dashboard. Se añadió `/salas/:roomId` como alias para enlaces directos en español.

## API

Se conserva `GET /api/v1/rooms/:roomId`, que devuelve el `RoomDto` existente. Ahora cualquier usuario autenticado con perfil completo puede consultar esos campos limitados para validar una invitación antes de unirse; antes el endpoint exigía ser miembro, lo que impedía la validación previa. Una sala inexistente o un ID de documento inválido devuelve `404 room_not_found`.

El resto de operaciones sobre la sala sigue validando membresía o propiedad como antes. La API no expone el documento Firestore completo.

## Frontend

- El dashboard y la barra de salas abren el mismo modal «Unirse a una sala».
- El formulario recorta el ID, evita la consulta si está vacío y valida caracteres permitidos antes de llamar a la API. Mientras la API comprueba la sala, muestra carga y bloquea nuevos envíos. Un error de sala inexistente se muestra junto al campo.
- Si la sala existe, el formulario navega a `/rooms/:roomId` y pasa el `RoomDto` validado para reutilizarlo sin una segunda consulta.
- Al abrir `/rooms/:roomId` o `/salas/:roomId` directamente, la página valida el ID y consulta la API antes de montar la llamada. Por tanto, primero se resuelve el acceso a la ruta mediante `PrivateRoute`; sin sesión se redirige al login y el `state.from` existente permite volver a la ruta solicitada. Si no existe, se muestra un mensaje y no se crea el socket ni se solicitan permisos de cámara/micrófono.
- Después de validar, `RoomPage` usa los hooks existentes para abrir un único socket y emitir `room:join`. Al abandonar la vista, el hook existente emite `room:leave` y cierra el socket.

## Contrato Realtime (existente, reutilizado)

El socket se autentica en el handshake con el ID token Firebase de la sesión. El servidor obtiene el UID del token; el cliente no manda identidad.

| Dirección | Evento | Payload | Resultado |
| --- | --- | --- | --- |
| cliente → servidor | `room:join` | `{ "roomId": "<id>" }` | Ack `{ ok: true, data: { roomId, online } }`; error `invalid_payload`, `room_not_found` o `internal_error`. |
| servidor → participante nuevo | `room:state` | `{ roomId, socketId, participants }` | Estado inicial de peers de la llamada. |
| servidor → demás sockets | `participant:joined` | `{ roomId, socketId, user, media, screenStreamId }` | Se emite una vez cuando ese socket entra. |
| cliente → servidor | `room:leave` | `{ "roomId": "<id>" }` | Ack `{ ok: true, data: { roomId } }`; si no estaba unido, `not_in_room`. |
| servidor → demás sockets | `participant:left` | `{ roomId, socketId, uid }` | Se emite al salir explícitamente o desconectarse. |

Al unirse por primera vez, Realtime escribe el perfil del participante en `rooms/{roomId}/participants/{uid}` y agrega su UID a `memberUids` en una transacción. Esos datos representan membresía histórica y permiten listar salas e historial; no se eliminan al salir. La presencia en línea es independiente y vive por socket en memoria. `PresenceService.leave` evita emitir dos salidas si `room:leave` precede a la desconexión.
