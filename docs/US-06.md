# US-06 — Crear y Ver Salas Propias

**Proyecto:** NEXORYX — `Nexoryx_frontend`
**Historia:** US-06 · «Crear y Ver Salas Propias»
**Estado:** implementado y verificado localmente (lint y compilación)
**Documento:** explicación y justificación de los cambios realizados

## 1. Propósito

Este documento explica qué se implementó para cumplir la historia US-06 del backlog refinado, por qué se tomaron las decisiones técnicas y de accesibilidad, y qué quedó deliberadamente fuera de alcance. Sirve como sustento para revisar el cambio en un PR y para que otra persona del equipo pueda continuar el trabajo sin reconstruir el contexto.

La historia pide que un anfitrión pueda crear salas de estudio y verlas en su panel para organizar sus espacios. El alcance acordado fue concreto: crear una sala y entrar a ella como anfitrión, listar las salas propias en el dashboard, validar el nombre, permitir copiar el ID con confirmación accesible e incluir los estados de carga, vacío, error y éxito.

## 2. Resumen de la solución

La funcionalidad se integró en el shell autenticado existente, sin crear una aplicación paralela ni una nueva ruta de navegación:

- Una capa de servicio encapsula las llamadas a la API de salas usando el cliente HTTP autenticado que ya existía.
- Un proveedor de estado comparte la lista de salas entre el dashboard, la barra lateral y el diálogo de creación, de modo que las tres vistas muestran la misma información.
- Un diálogo accesible reutiliza los componentes base del proyecto para crear la sala y entrar a ella.
- El dashboard presenta los estados de carga, vacío, error y éxito, además de la lista con nombre e ID y la acción de copiar el ID.
- No se modificó el backend ni se introdujo acceso directo a Firestore desde el navegador.

## 3. Criterios de aceptación y cobertura

| Criterio de US-06 | Cómo se cumple |
| --- | --- |
| Creación exitosa | El formulario valida el nombre y llama a `POST /api/v1/rooms`. La API genera el ID y registra al creador con rol `owner`. Al recibir la sala, la interfaz la agrega a la lista, anuncia el éxito y navega a `/rooms/:id` para entrar como anfitrión. |
| Dashboard vacío o con salas | `RoomsProvider` carga `GET /api/v1/rooms` una vez por sesión del shell. Si no hay salas, muestra un mensaje amigable; si hay, muestra una lista con nombre e ID de cada una. |
| Nombre inválido | La validación recorta espacios y rechaza el nombre vacío o de más de 60 caracteres. El error aparece junto al campo, asociado mediante `aria-describedby`, y no se ejecuta ninguna petición. |
| Copiar ID | Cada sala tiene un botón «Copiar ID». El ID se copia al portapapeles, la interfaz confirma con el texto «Copiado» y se emite un anuncio accesible sin mover el foco. |
| Estados de carga, vacío, error y éxito | El dashboard y la barra lateral reflejan el estado de la consulta. El diálogo muestra el estado de envío, bloquea el doble envío y conserva el formulario abierto si la API falla, con un mensaje accionable. |

Además de los criterios, se respetaron las restricciones explícitas: habilitar solo «Crear sala» y la visualización de salas, mantener `SoonButton` para las funciones futuras y no confundir «entrar a la sala» con implementar chat o videollamada.

## 5. Decisiones de diseño y arquitectura

### 5.1. Usar `GET /api/v1/rooms` y no `GET /api/v1/rooms/mine`

El backlog menciona `GET /api/v1/rooms/mine`, pero el backend actual documenta e implementa `GET /api/v1/rooms`. La ruta real devuelve las salas en las que el usuario es dueño o miembro, ordenadas por última actualización, y es la que aparece en la documentación Swagger y en el controlador de salas.

Se usó el contrato que existe en código. No se agregó la ruta antigua al backend ni se duplicó lógica para imitar el backlog, porque hacerlo habría creado una segunda fuente de verdad y un cambio de backend fuera del alcance de una historia de frontend. La decisión quedó documentada también en el servicio, para que la discrepancia no vuelva a introducirse.

### 5.2. Un proveedor de estado en lugar de consultas independientes

El dashboard, la barra lateral del shell y el diálogo necesitan la misma lista. Si cada vista consultara la API por su cuenta, se duplicarían peticiones y podrían aparecer estados contradictorios, por ejemplo una barra lateral que dice que no hay salas mientras el panel muestra una recién creada.

`RoomsProvider` centraliza la carga y expone un estado único con tres formas: cargando, error con mensaje y éxito con salas. También expone la recarga manual y el alta local de una sala creada, de modo que la lista se actualiza de inmediato sin una segunda petición. El proveedor envuelve el shell autenticado, por lo que se monta una sola vez por sesión y persiste al navegar entre el panel y una sala. La barra lateral y el panel consumen el mismo estado, lo que mantiene la interfaz coherente.

### 5.3. El diálogo reutiliza los componentes base

El formulario se construyó con `Modal`, `FormField` y `Button`, que ya resuelven el foco atrapado, el cierre con Esc, el retorno del foco, la asociación de etiqueta, ayuda y error, y el estado de carga. Reutilizarlos evita introducir un patrón de diálogo o de formulario distinto al resto del producto y mantiene la identidad visual.

La validación del cliente replica la regla del backend (`ROOM_NAME_MAX_LENGTH = 60`) para mostrar el problema antes de cualquier petición. El nombre se recorta antes de enviarlo y antes de medirlo, igual que hace el DTO del backend. El contador de caracteres es visual y está oculto a lectores de pantalla, para no generar ruido mientras se escribe; la ayuda y el error sí se anuncian porque están enlazados al campo.

Solo se expone el nombre. El DTO del backend admite una descripción opcional, pero US-06 no la pide, así que no se inventó un campo adicional en la interfaz.

Si la API rechaza la creación, el diálogo permanece abierto, conserva lo escrito y muestra un mensaje que explica qué hacer: sesión expirada, perfil incompleto, nombre inválido, servidor no disponible o falta de conexión. Esto evita perder el trabajo del usuario y evita que un error se confunda con una creación exitosa.

### 5.4. Dos niveles de lista con la misma fuente de datos

El dashboard es la vista principal de la historia y muestra la lista completa: nombre, ID y acción de copiar. La barra lateral del shell ofrece una versión compacta para navegar entre salas sin salir de la vista actual; en pantallas pequeñas permanece oculta, y el riel lateral sigue ofreciendo «Crear sala» con nombre accesible.

Ambas listas se alimentan del mismo proveedor. La barra lateral también muestra los estados de carga, error y vacío, para no afirmar que no hay salas cuando la consulta aún no terminó o falló.

### 5.5. Entrar a la sala es navegar a la sala existente

Al crear una sala, la aplicación navega a `/rooms/:id`. El backend ya deja al creador como dueño y primer participante, y la página de sala existente lo trata como un participante más de la llamada. No se agregó chat, señalización nueva ni controles multimedia: la historia solo pide entrar como anfitrión, y esas capacidades pertenecen a otras historias.

Esta decisión mantiene el cambio pequeño y evita reescribir `RoomPage`, que ya tenía su propio ciclo de vida de medios, sockets y pares WebRTC.

### 5.6. Copiar el ID con confirmación visible y accesible

La copia usa la API de portapapeles del navegador y, si no está disponible o falla —por ejemplo en un origen servido por HTTP sin contexto seguro—, recurre a una selección temporal del texto. El resultado se refleja de dos maneras: un cambio visible en el botón («Copiado» o «No se pudo copiar») y un anuncio mediante el anunciador compartido de la aplicación.

El anuncio es cortés cuando la copia funciona y asertivo cuando falla. El foco no se mueve: quien usa lector de pantalla recibe la confirmación sin perder su posición. El estado visible se limpia a los pocos segundos para que el botón vuelva a su etiqueta original.

### 5.7. La capa de datos sigue la arquitectura existente

Todas las llamadas pasan por el cliente Axios del proyecto, que adjunta el token de Firebase de la sesión. El navegador no lee Firestore directamente. Esto respeta la regla del producto y evita duplicar reglas de autorización en el cliente.

### 5.8. Disciplina de alcance

Se habilitó únicamente lo que US-06 exige:

- «Crear sala» en el dashboard y en el riel.
- La visualización y la lista de salas en el dashboard y la barra lateral.
- La validación del nombre y la copia del ID.

Siguen con el comportamiento de `SoonButton` —visible, enfocable y con anuncio de la historia en la que llegan— «Unirse con enlace» (US-08), la unión por enlace, la edición y eliminación de salas (US-07), el chat (US-10 y US-11), las reacciones y los controles multimedia de historias futuras. No se convirtió `SoonButton` en funcional de forma global ni se tocó su implementación.

## 6. Accesibilidad (WCAG 2.2 AA)

| Criterio | Aplicación en el cambio |
| --- | --- |
| 1.1.1 Contenido no textual | Los iconos son decorativos y llevan `aria-hidden="true"`. Los botones de solo icono, como «Crear sala» del riel, tienen nombre accesible. |
| 1.3.1 Información y relaciones | Se usan secciones, encabezados y listas semánticas. `FormField` enlaza etiqueta, ayuda y error con el campo. |
| 1.4.3 y 1.4.11 Contraste | Se conservan los colores y tokens existentes del tema oscuro, revisados previamente para texto y bordes de campo. |
| 2.1.1 y 2.1.2 Teclado | Todos los controles son elementos nativos (`button`, `a`, `input`, `dialog`). El diálogo se cierra con Esc y no atrapa el foco fuera de sí mismo. |
| 2.4.3 y 2.4.7 Foco | El modal devuelve el foco al control que lo abrió y el foco visible global se mantiene. Al abrir el diálogo, el foco pasa al campo de nombre. |
| 3.3.1 y 3.3.3 Errores | El error se muestra en texto, explica cómo corregirlo y está asociado al campo con `aria-invalid` y `aria-describedby`. |
| 4.1.3 Mensajes de estado | Los cambios de estado se anuncian con el anunciador compartido, sin mover el foco. La confirmación de copia también es visible. |
| 2.4.2 Título de página | El dashboard conserva su título mediante `usePageTitle`; no se agregó una ruta nueva. |

La validación mueve el foco al campo inválido de forma intencional para facilitar la corrección; los anuncios de estado, en cambio, no mueven el foco.

## 10. Conclusión

El cambio cubre US-06 con una solución pequeña y coherente con la arquitectura existente: un servicio para el contrato real de la API, un estado compartido para evitar vistas contradictorias, un diálogo accesible construido con los componentes del proyecto y una lista con estados completos y copia confirmada del ID.

La decisión más importante fue seguir el contrato implementado (`GET /api/v1/rooms`) en lugar de la ruta antigua del backlog, sin modificar el backend. La segunda fue mantener el límite de la historia: crear y ver salas, entrar a la sala existente y dejar chat, llamada, unión por enlace y gestión de salas para sus historias correspondientes.
